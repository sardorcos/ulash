# ADR 0001 — Первый работающий срез

Дата: 20 ноября 2026. Статус: принято для 0.1.0, не заменяет ТЗ v1.

## Решение

Сначала реализован единый Flutter/Dart foreground push: получатель принимает HTTPS, отправитель инициирует соединение. Общий Dart core отделён от UI и платформенной среды. AppRuntime задаёт защищённое хранилище, сетевые разрешения, discovery и адреса; native main использует только native-конфигурацию. MemorySecretStore допускается явными изолированными тестами и CLI с временным временем жизни.

## Почему

Это позволяет проверить реальные TLS, consent, файловую запись и восстановление до включения более сложных lifecycle-режимов и host-selection/pull. Код UI не имитирует сетевой успех. Все числа прогресса исходящей передачи берутся из устойчивого журнала получателя; окончательная доставка требует корректного полного набора committed receipts.

## Сетевые свойства

- Начальный адрес передаётся QR-приглашением и проверяется по SPKI.
- На каждом новом TLS-соединении SPKI проверяется в callback с пустыми roots и повторно по peerCertificate до передачи HTTP клиенту.
- Автообнаружение выдаёт неподтверждённые адреса; оно не может менять ключ доверенной пары.
- `canPullClient` и background-capabilities равны false. Отсутствующие возможности нельзя скрывать за интерфейсом.
- HTTP push использует HEAD/PATCH и offsets tus 1.0; создание и авторизация ресурса — наш протокол `/v1`.
- Запуск HTTP Host, пауза/возврат приложения и выключение приёма сериализованы. Явное receive OFF имеет приоритет над lifecycle resume.

## Хранение

SQLite требует WAL/FULL. Подтверждение offset следует после file flush и commit журнала. Итоговый файл сначала проверяется SHA-256, затем фиксируется commit intent, выполняется rename и сохраняется committed. Source остаётся immutable staging copy. Локальные конечные каталоги используют сгенерированный Sink storageIncarnationId, чтобы отправитель не управлял системным именем каталога.

Ошибочная или частично выполненная передача имеет отдельный неуспешный результат. Новый запуск после failed receive требует нового offer; автоматический destructive reset отсутствует. Намерение отмены сохраняется независимо от последнего снимка удалённого состояния, включая потерю ответа и restart.

## Последствия и открытые задачи

Оба мобильных приложения должны оставаться открытыми. IPv4 и один writer на получателе — граница этой альфы. Нужны аппаратные проверки, host role selection/pull для iOS, native services/extensions, IPv6, retention/quota, atomic native filesystem hardening и экспорт. Оценка готовности v1 определяется gates из ТЗ, а не числом зелёных тестов.
